# ordinances/ — adopted Sandy City ordinances (Legistar-sourced)

Additive dataset: **adopted zoning/land-use (and all other) ordinances, 2020–2026**,
built from the **Legistar Web API** and linked to `meeting_minutes/all_votes.csv`. Read
`AVAILABILITY.md` for coverage/gaps. This file is the method + the independence caveat.

## Which artifact for which question
- **"What ordinances did Sandy adopt / which rezones-annexations-code-amendments?"** →
  `index.csv`, filter `adopted=yes` (and `land_use=yes` for zoning/land-use only).
- **"Full enacted text of ordinance NN-NN?"** → the PDF at that row's `path`
  (`raw/ordinances/<adoption-date>_<num>.pdf`), signed ordinance where available.
- **"How was it adopted / who voted?"** → follow `matched_motion_date` +
  `matched_motion_no` into `meeting_minutes/all_votes.csv` (only trust `high`; spot-check
  `medium`; `low` = consent-calendar/fuzzy; `none` = unmatched).
- **Current codified zoning text** → Municode `https://library.municode.com/ut/sandy`
  (browser only; not mirrored). Do **not** use `sandy.municipal.codes` (403 bot-block).

## Legistar API endpoints (GET-only, no key; base `https://webapi.legistar.com/v1/sandyutah/`)
- **Ordinance index**: `matters?$filter=MatterTypeId eq 53 and MatterIntroDate ge
  datetime'2020-01-01'&$orderby=MatterIntroDate` → `MatterId`, `MatterFile`,
  `MatterTitle`, `MatterIntroDate`, `MatterAgendaDate`, `MatterStatusName`.
  (`MatterName` is always null; the subject is in `MatterTitle`. `MatterEnactmentNumber`
  is **always null** — the real ordinance number is NOT in the matter record; see below.)
- **Adoption**: `matters/{id}/histories` → the passing action. A matter is treated as
  **adopted** here iff it has a **City Council** history row whose action ∈
  {adopted, approved, adopted as amended} and `MatterHistoryPassedFlagName != 'Fail'`
  (Pass **or null** — Legistar leaves the flag null on a few genuine adoptions;
  `Fail` = the adopting motion failed). The action date is the adoption date.
- **Enacted text + real ordinance number**: `matters/{id}/attachments` →
  `MatterAttachmentHyperlink`. The **ordinance number** (`YY-NN`, e.g. `26-05`) is parsed
  out of the **attachment names** (e.g. "Signed_Ordinance_26-05", "24-10 Ordinance-…"),
  NOT from any matter field. A `-C` suffix (e.g. `24-17C`) = a **resolution**, excluded.
  When two numbers appear, the one whose `YY` matches the adoption year wins (guards
  against typo filenames — e.g. a "Signed_Ord 12-13" for the 25-13 annexation).

Raw provenance retained verbatim in `raw/api/` (the matters query + per-matter
`histories/<id>.json` and `attachments/<id>.json`, 341 files, hashed in
`raw/api/_fetch_log.jsonl`) and the enacted PDFs in `raw/ordinances/` (fetched via
`scripts`' `polite_fetch.py`; log in `raw/ordinances/_fetch_log.jsonl`).

## Linkage method + the INDEPENDENCE CAVEAT (read this)
`match_confidence` joins each adopted ordinance to a vote motion by **adoption date +
ordinance number cited in the motion text**: `high` = date AND number both in the motion;
`medium` = date + subject agree but the number differs / isn't restated / was enacted as
a resolution; `low` = meeting held but only a Consent-Calendar/unnumbered motion (or the
number appears on a different date); `none` = unmatched (kept empty — **never** forced).

**The number match is strong but NOT fully independent.** The ordinance index comes from
Legistar `matters`, and the council agenda items behind the votes were generated by the
**same** Legistar system, so a matching number partly reflects one shared upstream. What
*is* cross-document is that the **ordinance number here is read off the signed PDF's
attachment name**, while the vote layer's number is transcribed from the **council
minutes** — so a `high` match genuinely corroborates two different documents, and a
**conflict is a real audit signal** about the minutes (see `AVAILABILITY.md` findings §1:
`22-07`/`24-03`/`24-17`/`24-25`/`25-07`). Do not "fix" the vote layer from this dataset —
it is additive; log discrepancies only.

A genuinely adopted ordinance with **no** vote row on its adoption date would be an audit
signal against the minutes/vote layer. There is currently **one** unmatched adopted
ordinance (`26-50`) and it is only a **coverage lag** (adopted 2026-06-23, after
`all_votes.csv`'s 2026-06-02 end), not a defect.

## index.csv columns
Standard six: `date` (= adoption date if adopted, else agenda/intro date), `title`
(=`MatterTitle`), `source_url` (the retained PDF's hyperlink, else the Legistar
LegislationDetail page), `retrieved_date`, `format` (`text` for PDF rows, `json` for
metadata-only rows), `extraction_method`. Plus:
`ordinance_no` · `adoption_date` · `path` (dataset-relative, incl. `raw/`) ·
`land_use` (yes/no) · `result` (§9 contract column; blank where not recorded) ·
`matched_motion_date` · `matched_motion_no` · `match_confidence` ·
`matter_id` · `matter_file` (Legistar file/case no., often a planning case like
`REZ…`/`ANX…`/`CA…`, NOT the ordinance number) · `matter_status` · `adopted` ·
`legistar_matter_url` · `signed_pdf_url` · `linkage_note`.

## Rebuild
Idempotent, GET-only, additive. Re-pull the three API layers (matters + per-matter
histories/attachments), re-derive adoption/number/land-use, re-link to `all_votes.csv`,
re-fetch any new signed PDFs via `polite_fetch.py`. Validate with
`.claude/skills/expand-city-sources/scripts/validate_dataset.py`. There is **no extracted
text corpus** (PDFs retained as binary; the index is metadata), so `screen_corpus.py`
does not apply.
