# campaign_finance/ — Washington County COUNTY-OFFICE campaign finance

Additive dataset, as-of **2026-08-01**. Filings by candidates for and holders of the
**nine Washington County county offices** — Commission Seats A/B/C, Attorney, Clerk/Auditor,
Sheriff, Assessor, Recorder, Treasurer.

`washington_county` is a **db-less LIGHT+** entity (root `CLAUDE.md`): there is no
`washington_county/db/`, and this dataset does not need one. It is a **document + text
corpus with an index**, exactly like the county's `plans/` and `ordinances/` modules, and it
federates on the same terms.

- **How the record is structured, and every channel checked** → **`RECON.md`**
- **What each source held, and the honest gaps** → **`AVAILABILITY.md`**
- **Donor / candidate personal data policy** → **`PRIVACY.md`**
- Contract for a future money layer → `scripts/campaign_finance/SCHEMA.md`

---

## The one form family, and why every era looks different

**One statutory form runs the whole record**: "FINANCIAL CAMPAIGN REPORT", citing **Utah Code
17-16-6.5**, filed with the County Clerk, with the distinctive triple
**`TOTALS FROM LAST REPORT + TOTALS FOR THIS REPORT = CUMULATIVE REPORT`** over four lines
(contributions >$50, aggregate ≤$50, expenditures, ending balance) plus Form "A"
(contributions) and Form "B" (expenditures). It is legible on the **2006** filing and on the
**2025** filing alike.

What changes is **how the county published it**, and that governs everything downstream:

| Era | Published as | Machine-readable? |
|---|---|---|
| **2006, 2016–2025** | **handwritten** paper, scanned to image-only PDF | **No.** `pdftotext` = 0 chars. OCR reads the *printed* labels ("Recorder", "Clerk-Auditor", "Assessor") but the *handwritten values* garble ("`+e EASURER`", "`$ 94/ q fF`"). |
| **2008** | scanned PDFs, **plus the clerk's web page printing each filer's totals in HTML** | **The PDFs are not; the page's HTML totals are** — captured in `portal_stated_totals.csv`, the only machine-readable amounts that exist for 2008. |
| **2010–2013** | **born-digital PDF**, split 3 ways per filing (`Summary` / `Contributions` / `Expenditures`) | **Yes** — real text layer, itemised ledgers with recipient, date, amount, in-kind flag, description. |
| **2014–2015** | **`.xls` workbooks**, same 3-way split | **Yes, best of all** — actual spreadsheet cells. |

⚠ **Do not use a character-count threshold to decide "born-digital vs scan" here.** Several
born-digital tables are legitimately **empty** (a candidate who reported nothing), and OCR'ing
them produces pure noise (`es es ee`). `build_text.py` uses **`pdffonts`** — a PDF carrying
embedded text fonts is born-digital however little text it holds.

## Reading the index: office is decided by the DOCUMENT, not the label

Portal labels lie here more than usual (`AVAILABILITY.md` §5 lists eight verified defects,
including a file named `…Contributions - Greg Aldred.pdf` that **contains a County Candidate
Summary**). So `index.csv` records what each source said and which one was believed:

| column | meaning |
|---|---|
| `office` | canonical county office. **`Commission (seat not stated)`** is a real, honest value — the source named the body but not the seat. |
| `office_source` / `office_confidence` | `document` (**high**) → `portal_listing` (medium) → `person_roster` (medium) → `filename` (low). **Filter `office_confidence='high'` for a document-verified subset.** |
| `roster_match` | when `office_source=person_roster`, the exact `FIRST LAST @cycle` key that matched |
| `document_office_raw` / `document_candidate` | verbatim from the file, OCR garble included |
| `portal_office` / `portal_label` | verbatim from the county's page or listing |
| `label_conflict` | set only when document and portal name **different specific** offices |
| `reporting_year` / `reporting_year_source` | the year the SOURCE attaches to the file |
| `cycle_year` / `cycle_year_source` | the **even-year election cycle**: `document` (the form printed an "Election Year"), `derived:january-close` (a January filing closes the PRIOR year's cycle), `even_reporting_year`, or **blank when not determinable — never guessed** |
| `cycle_parity_flag` | fires on an odd cycle year (see below). **Currently zero rows.** |
| `doc_kind` | `statement` / `summary` / `contributions` / `expenditures` — read from the document, **not** the filename |
| `n_identical_copies` / `alt_source_urls` | the archive lists some files under both `http://` and `https://`; identical sha256 is collapsed to one row with the other URLs retained |
| `sha256`, `bytes`, `channel`, `source_archive`, `wayback_timestamp`, `fetch_url` | provenance for every byte |

### The person→office roster (`office_source=person_roster`)

Where a handwritten form's office line is unreadable, office is resolved from a roster built
**only from sources that state an office**: the live county page's own office/candidate table,
the archived listing pages' office headings, the 2008 clerk page, every document that printed
its own office line, **and the county's own certified canvass**
(`../elections/washco_results_long.csv`, read-only — county contests 2018–2024).
Keyed by `(person, cycle)` because filers move between seats — **Chris White** ran for
Commission **Seat C** in 2012 and **Seat A** in 2014; **Chuck Goode** for **Seat B** in 2022
and **Seat C** in 2024. **A person with two different offices in one cycle is dropped as
ambiguous, never resolved by preference.**

### Cycle parity — the check that catches the header false-positive

The 17-16-6.5 header proves *county-clerk-filed*, **not county office**: Local School Board
candidates file on the same form, and so do special districts (this county's instance:
6 **Northwestern Special Service District** filings in 2021 headed "WASHINGTON COUNTY
CANDIDATE FINANCIAL CAMPAIGN REPORT"). Washington County offices are elected in **even years
only**, so an odd `cycle_year` is a red flag. **Every row here resolves to an even cycle
year.** An odd *reporting* year is normal and unflagged — the **annual** officeholder report
is filed each January (hence 2011 / 2015 / 2025 reporting years with a blank `cycle_year`).

### The BORN-DIGITAL itemized layer (built 2026-08-02, TRANCHE 3 Phase A)

Wired to the registered `washco_split` family — the family that exists because **one logical
filing here is up to three published files, and the reconciliation anchor (the `County
Candidate Summary`) sits in a DIFFERENT FILE from the itemised rows it must reconcile
against.** The file-set is grouped on this module's own
`extract_born_digital.filing_key` (already materialised as each cache's `files` list, primary
= the `doc_kind='summary'` file) — the identical contract as the shared driver's
`group_fn` / `group_primary_fn` — and handed to `family.parse_group(parts, meta)` with the
filing's own ISO `deadline`.

| | count |
|---|---:|
| born-digital `summary_sheet` file-sets handed to the family | **102 of 206 filings** |
| contribution sides reconciling exactly → shipped | **15** |
| expenditure sides reconciling exactly → shipped | **39** |
| distinct filings carrying at least one itemized row | **43** |
| rows emitted | **181 contributions · 308 expenditures** |
| rows carrying `geometry` | **489 of 489 (100%)** — real `Sheet1!F5` cell references on the `.xls` generations, `p:l:c` spans on the PDF ledgers |

- **Scope is the 2010–2015 born-digital generations ONLY.** The **4 ledger-only 2008
  `Detailed … Report` postings emit NO rows by design**: they print no totals at all, so there
  is nothing to reconcile a ledger against; their counted sums live — labelled *counted*, never
  *stated* — in `portal_reconciliation.csv`. The 100 handwritten cover forms and their vision
  caches were not touched, and **0 of 206 `stated_*` values changed.**
- **Why 15/39 and not 102/102, and why that is the county's property rather than a defect.**
  The Filing-style finding below is the whole story: **the Summary rows are PER-PERIOD
  increments while the Contributions/Expenditures ledgers restate the WHOLE CYCLE TO DATE.** On
  a candidate's first filing of a cycle the two coincide and the ledger reconciles to the cent;
  on every later filing they are *different quantities*, and making them agree would require
  arithmetic of ours (summing prior periods), not the county's. Those sides are **withheld with
  that reason written into `filing_totals.notes`** — not published as a mismatch, not adjusted.
- **`is_incremental` on the itemized rows is `False`, deliberately**, even though the FILING's
  regime is incremental: the rows come from the LEDGER, which restates the cycle to date. The
  `filing_regime` column describes the STATED figures; the row flag describes the rows. Marking
  ledger rows incremental would make a naive cycle sum double-count. (This is why the same
  donor row legitimately appears under two consecutive filings of one cycle — e.g. Steven G
  Caplin $1,000.00 dated 2014-03-28 under both the 4/4/2014 and 6/17/2014 file-sets.)
- **Roles come from DOCUMENT CONTENT, never filenames** — the group's primary is the file whose
  `doc_kind` is `summary`, and the county's own misspelling `All Expeditures for` is matched as
  printed, never "fixed".
- **PRIVACY:** the ledgers print a donor's street address on the line below the name (`.xls`)
  or in the description column; only `donor_city` / `donor_state` are emitted
  (`common.split_city_state`) and the street portion is discarded and never stored. The two
  digit-bearing `donor_raw` values are the county's own AGGREGATE lines
  (`5 Donations of under $50.00`), flagged `needs_review=1`.

### Where each stated figure comes from — the one decision that matters

The two published generations put the filing's own number in **different columns**, and getting
this wrong silently double-counts or under-counts a whole cycle:

| cache `sheet_type` | source shape | the filing's figure is | `is_incremental` |
|---|---|---|---|
| `cover_form` (100) | handwritten/typed 17-16-6.5 cover, 2006 + 2016–2025 | the **CUMULATIVE** column (`LAST + THIS = CUMULATIVE`) | **false** — a cycle total is the **LATEST** report, never a sum |
| `summary_sheet` (102) | born-digital `County Candidate Summary`, 2010–2015 | the **per-period row** for that deadline | **true** — but the companion ledgers restate the whole cycle, so a cycle total is the **LEDGER**, not the sum of summary rows |
| `ledger_only` (4) | 2008 `Detailed … Report` pairs + one 2011 pair | **nothing — the filing prints no totals** | n/a |

### Caveats carried in `filing_totals.notes` (all greppable)

- **`CROSS-CHANNEL RE-POST`** — **12 rows / 6 filings.** The county re-posts filings as it
  migrates CMS, so the *same report* appears on two channels (state + 2010 archive; `live_outpost`
  + `live_wp`). **Count each report ONCE.** Detection is deliberately conservative: same filer,
  same filing date, identical stated figures, **and different channels** — because a filer with
  no activity between two deadlines files two DIFFERENT reports with identical (zero) figures,
  and this record has several of those. Same-channel look-alikes are left alone.
- **`CUM-BLANK-THIS-PRESENT`** — 2 filings. The filer filled LAST + THIS and left CUMULATIVE
  empty. The form's arithmetic would complete it, but that would be *our* arithmetic published
  as the county's stated total, so `stated_*` stays blank and the figure the filer *did* state
  is written verbatim into the note. Nothing is lost; nothing is invented.
- **`LEDGER-ONLY filing`** — 4 filings, stated totals honestly blank.
- **11 filings have no stated contribution or expenditure total at all** — 4 ledger-only, the
  rest filers who left the cumulative column blank or wrote `None/Zero` / `-` rather than a
  figure. Blank ≠ zero here, ever.

### The stated-totals cache (`vision/*.json`) — 206 files, TWO provenances

**Cache key = `sha1(filing_key)[:8]`**, where `filing_key` is `"FILE|<path>"` for a
self-contained filing and `"<channel>|<deadline>|<CANDIDATE>"` for one split across a
Summary + Contributions + Expenditures set. **This deviates from the repo-standard
`sha1(index_path)[:8]` deliberately and necessarily** — a filing here is not a file, so no
single index path can key it. Every cache carries `filing_key`, `primary_path` and a `files[]`
list with per-file `sha256`, so the key is always re-derivable from the cache itself.

- **`transcribed_by: "vision-transcribed(...)"` — 100 caches, HAND WORK, NOT REGENERABLE.**
  Backed up under `_backups/2026-08-01-county-acquisition/washington_county-vision/`.
- **`transcribed_by: "born-digital-read(...)"` — 106 caches**, regenerated by
  `extract_born_digital.py` from `.xls` cells / the PDF text layer. Byte-reproducible.

**Independent verification (2026-08-02):** an 11-cache stratified sample of the vision half was
re-rendered at 200dpi and re-read blind. **156 of 156 money cells matched — no wrong digit, no
transposition, no column swap**, with correct blank/zero/dash discipline on struck-circle zeros,
accounting dashes and parenthesised negatives; cover candidate+office **13/13**. The vision
transcription is adopted in full. The same audit found the weakness is *not* the numbers but the
annotation layer — see "Defects found and fixed" below.

### But the data DOES reconcile — hand-verified 2026-08-01, re-confirmed by the build

### Defects found and fixed 2026-08-02 (the resumed pass)

The determination file is **also the correction path when the cascade classified a file
WRONGLY**, not just when it failed. Four such rows were added after re-reading the page images:

- **Gil Almquist 2016 × 3 filings** — indexed as **Commission Seat A**; every form's office
  line reads verbatim **"Office: Washington County Commissioner seat C"** (and one county
  filename says "County Commission Seat C"). The cascade took Seat A from the `person_roster`
  / live-page listing, both of which group Almquist under the seat he holds **now**. This is
  precisely the `(person, cycle)` hazard this doc already warns about — **the roster must never
  outrank a legible document.** Corrected to Seat C.
- **Slade Hughes 2020** — indexed `Commission (seat not stated)` from the filename tier; the
  handwritten line reads **"County Commission Seat C"**. Corrected. (Its sibling, Douglas
  Wulfenstein 2020, genuinely states only "County Commission" and **correctly remains**
  `Commission (seat not stated)` — the honest value is not a bug.)
- **One vision cache's `notes` was factually wrong** (`ab150606`, Almquist 6/17/2016). It
  asserted the figures came from the PDF text layer (that PDF's text layer is **5 bytes** — it
  is a scan), gave Form A's total as `$20,917.51`, cited a `Grand Total 20,449.51`, and recorded
  a **"FILER INCONSISTENCY"**. Re-reading pages 3 and 5 at 200dpi: Form A prints
  **`$20,117.51`**, Form B prints **`$20,117.51`**, there is **no "Grand Total" line**, and the
  cover's line 1 = Form A = Form B = 20,117.51 with balance 0.00 — the filing is **internally
  consistent and there was no inconsistency to retain**. The note is corrected in place and
  says so; **the transcribed money values were verified correct and are unchanged.**
  *Lesson for the next pass: a `notes` field reads as verified provenance. Never write a figure
  into one from memory of a page you are no longer looking at.*
- **`build_finance.py` reads `office` from the LIVE `index.csv`, never from the cache's
  `index_office`** — that field is a snapshot frozen at transcription time, and the vision
  caches are never regenerated, so it goes stale the moment an office is corrected. It did.

## `portal_stated_totals.csv` — what it is and is not

**7 county-office filing snapshots** transcribed **verbatim from the county's own
rendered 2008–2010 pages**, which printed each filer's submitted totals (contributions /
expenditures / balance, split "Beginning Balance" vs "Party Convention") directly above the
links to that filer's PDFs. It is **not** a parse of any filing and **not** the SCHEMA.md
money layer — it is a **second, independent statement of the same figures**, and therefore
the reconciliation anchor a future vision pass should be scored against. It shows, for
example, Lin Alder's 2008 Commission race escalating **$5,765 → $14,070 → $38,845** across
the June / August / October deadlines.

## Do-nots

- **Never quote a dollar figure from `text/`.** Every PDF-era amount is either handwritten
  OCR (garbage) or absent. Amounts are trustworthy only in the born-digital 2010–2015 files,
  in `filing_totals.csv` / `vision/*.json`, and in `portal_stated_totals.csv`. For anything
  else, open the file in `raw/`.
- **Never sum `filing_totals` rows to get a candidate-cycle total.** Two different reasons in
  the same table: `cover_form` rows are CUMULATIVE (take the latest), and `CROSS-CHANNEL
  RE-POST` rows are the same report published twice (count once). Read the row's `notes`.
- **Never sum the `summary_sheet` rows of a 2010–2015 cycle either** — those are per-period
  increments whose companion ledgers already restate the cycle to date.
- **Never treat a blank `stated_*` as `0`.** Blank means the filer left the cell empty, wrote
  `None/Zero`/`-`, or filed a ledger with no totals sheet at all.
- **Never let `person_roster` or a filename override a legible office line** — it produced the
  only wrong office values this dataset has had (Almquist 2016). Corrections go in
  `office_determinations.csv` with the verbatim office line quoted as evidence.
- **Never treat `index.csv` as a complete census of filings.** `outpost.washco.utah.gov`
  cannot be enumerated (403 on every directory) and Wayback never crawled it; the
  2016–2024 listing page was never archived with content. We have everything the county has
  ever *linked*, not everything it holds (`AVAILABILITY.md` §4).
- **Never join these filers to municipal candidates by surname.** St. George's municipal
  filings are a separate population in `st_george_city_council/campaign_finance/`; the county
  and the city run different disclosure regimes (17-16-6.5 vs 10-3-208).
- **School board is out of scope, not absent from the record** — it is ledgered in
  `excluded_school_board.csv` with hashes, so re-fetching is deterministic if scope changes.
- Don't "fix" `All Expeditures for` — that is the county's own spelling in its workbooks.
