# Holladay City Council — data repository

Canonical datasets about the Holladay City Council (with in-session **Redevelopment Agency**
and **Local Building Authority** sessions), Planning Commission, and municipal elections,
modeled on the Salt Lake City reference repo and conforming to the collection-wide standard at
`/Users/tysonwelsh/civic-data/SCHEMA_SPEC.md` (check with `scripts/validate_city.py`). Built by
the `build-city-data-repo` skill. Data floor: **2020** (Holladay incorporated **1999** — full
modern council record; 2020 is a normal floor, not an incorporation edge).

```
meeting_minutes/      Council + in-session RDA/LBA minutes (markdown) + extracted votes
                      (all_votes.csv, motions_std.csv) + retained raw/ originals
planning_commission/  SAME schemas for the Planning Commission (body=PlanningCommission)
public_comments/      AVAILABILITY.md — comments are HONEST-EMPTY (submit-only; no published
                      written-comment archive) — no all_comments_clean.csv by design
election_results/     Salt Lake County SOVC filtered to Holladay council+mayor races (2007–2025)
geo/                  OFFICIAL 5-district polygon layer + address/point -> council district tool
db/                   relational SQLite (civic.db; build_db.py + build_referrals.py; regenerable)
weeks/                DERIVED weekly bundles tying minutes + votes together
build_weeks.py        regenerates weeks/ (Council meets THURSDAY; PC meets Tuesday)
fetch_new.py          incremental refresh driver (probes PMN bodies 388 council / 389 PC)
recon.md              map of this city's data sources (provenance) — written BEFORE acquisition
SOURCES.md/sources.csv per-document provenance index (portal, URL, extraction method)
VERIFICATION.md       independent QA + external election cross-check (§6 there)
```

## The structural facts that make Holladay different

1. **The MAYOR VOTES — max council roll = 6.** Holladay uses Utah's **Council–Manager** form:
   **five district councilmembers (D1–D5) plus a separately-elected, voting Mayor**, and an
   appointed **City Manager as the executive**. A full named council roll therefore tops out at
   **6** (`… Mayor Dahle-Aye`), never 5. There are **365 mayor vote-rows**. This is the *opposite*
   of Taylorsville/South Jordan (executive mayor, does NOT vote, roll of 5) and matches Millcreek
   (mayor votes). The PC has **no mayor** and its roll tops out at **7** (7-member commission).
2. **Roster turned over at the Jan-2026 seating** — who-voted analysis must be **date-aware**:
   Mayor **Dahle → Fotheringham**; D1 **Brewer → Sundwall**; D3 **Fotheringham → Bradley**.
   Continuing: **Durham** (D2), **Quinn** (D4), **Gray** (D5, from 2024). `roster.csv` is
   **OBSERVED** (regenerated by `validate_votes.py` from the actual vote rows — never
   hand-authored); a person is flagged `mayor_rows_seen=yes` when the source printed them as
   `Mayor <Name>`.
3. **In-session RDA and LBA.** The Council **recesses and reconvenes** as the **Redevelopment
   Agency** and the **Local Building Authority** inside a single council minutes doc; those
   motions are re-tagged `body=RDA` (60 vote rows / 21 motions) and `body=LBA` (12 rows / 3
   motions) by a section walk. A standalone RDA "Board Meeting" doc (its own Chair/Board-Member
   roster) is routed wholly to `body=RDA` by slug. There is **no separate RDA/LBA portal** to
   acquire — same practice as Taylorsville's in-record RDA.
4. **PMN is the spine.** Every minutes doc is a **born-digital** `pdftotext -layout`-clean PDF
   from **Utah Public Notice** — council **public body 388**, PC **public body 389**
   (`utah.gov/pmn/files/<id>.pdf`; the `<id>` is the trailing filename token and the
   `source_url`). No OCR anywhere (corpus screen: 0 stubs, 0 low-alpha, both bodies).
   **One documented exception (2026-07-31):** PMN notice 990511 (Council **2025-05-01**)
   published the **WRONG minutes file** — its Meeting-Minutes attachment `1282121` is named
   `051525 CC Mtg.pdf` and is **byte-identical** to `1282125`, the 2025-05-15 minutes. Ingesting
   it had minted a **phantom 2025-05-01 meeting** double-counting 3 motions. The phantom was
   removed and the **true 05-01 minutes recovered from the city SuiteOne portal**
   (`holladayut.suiteonemedia.com/event/GetMinutesFile/Minutes?mid=1156`, event 2903) — so the
   council `minutes_index.csv` now carries **one `source=suiteone` row** alongside 151 `pmn`
   rows (the PC index likewise carries 27 `source=wayback` rows). Details + evidence:
   `_removed_duplicates/2026-07-31-g8/README.md`. `fetch_new.py --fetch` now **hashes every
   downloaded PDF and refuses to index bytes already on disk under another meeting date**, so a
   refresh cannot re-create this phantom.
5. **Two vote-grammar eras.** **Legacy (2020–2021)** minutes print a **prose roll** ("The Council
   roll call vote was as follows: Council Members A, B, C and Mayor Dahle in favor [with X
   opposed]" → favor=Aye, opposed=Nay). **Modern (2022+)** prints a named inline roll
   (`Vote on Motion: Council Member Gray-Aye; …; Mayor Dahle-Aye`), some tokens as `-Yes/-No`.
   Both parse deterministically; **the printed `Yes/No` is NORMALIZED to Aye/Nay** (SCHEMA_SPEC
   §4) — `all_votes.csv` carries **zero** `Yes`/`No` values.

## Index + vote schemas are the collection standard
- `minutes_index.csv`: `date,year,title,slug,path,source,source_url,format,body` — one row per
  document on disk (`source=pmn`, `format=pdf-text`); the extra `body` column is a documented
  extension. Unrecoverable meetings live in `minutes_unrecovered.csv`, **never** as stub/wrong-doc
  rows.
- `all_votes.csv`: the 13-column standard
  (`date,year,title,body,motion_no,motion,motion_type,result,mover,seconder,member,vote,source`).
  **Only `result` is city-verbatim.** `motion_type` is a derived label; **`vote` is normalized**
  to the controlled vocabulary. Cross-city comparison goes through **`motions_std.csv`**
  (normalized outcome/tallies/motion_type_std) and the repo-root **`crosswalks/`** — never the raw
  `result`/`motion_type` strings.
- Raw originals are retained under each dataset's `raw/` and are never deleted.

## The prose-results quirk (read before quantitative claims)
Holladay `result` strings are **prose, not numeric tallies** ("Ordinance 2025-22 was adopted by a
unanimous vote."). So the validator's numeric-tally cross-check
(`validate_city.py` f.tally) matches **0/232** by design — this is a *source style*, not lost
data. The parsed outcome (Pass/Fail/Continued/Died) lives in **`motions_std.csv`** (1,012/1,030
motions carry a classified standardized outcome). Use `motions_std.csv`/the db for
outcome aggregation, and the `result` string only for the exact wording.

## How to analyze (which artifact for which question)
- **Aggregate / time-series**: the canonical flat tables — `meeting_minutes/all_votes.csv`
  (+ `motions_std.csv`) and `planning_commission/all_votes.csv`. Blank `member`/`vote` on a
  unanimous-consent motion is a **tally-only** honest gap (the source printed no names), not an
  extraction miss.
- **Relational / cross-body** (PC recommendation → council outcome; a member's record across
  bodies): `db/civic.db` — read `db/SCHEMA.md` first; start from `v_referral_chain`,
  `v_project_timeline`, `v_member_record`, `v_contested`. The `referral` layer is reconstructed +
  scored (**5 links, all medium** Council←PC) — respect the confidence column; Holladay's Council
  minutes are ordinance-number-keyed and carry no PC case numbers, so every cross-body link falls
  to subject + address + temporal.
- **Meeting-level / contextual**: the `weeks/<Thursday-week>/` bundle (start with `summary.md`).
- **By member**: join election winners (`election_results/holladay_races.csv`) ↔ votes on
  **person + year + district** (normalize names — election names are UPPER-CASE, `(NP)` suffix).
  Mind the **Jan-2026 roster drift**.
- **By geography**: `geo/address_to_district.py` resolves an address/lat-long to District 1–5
  against Holladay's **official** polygon layer (the Mayor is citywide, never returned).

## weeks/ and db/ are derived — regenerate, don't hand-edit
`python3 build_weeks.py` · `python3 db/build_db.py && python3 db/build_referrals.py`. Canonical
truth is the dataset folders (flat CSVs + minutes markdown + retained `raw/`); never edit files
under `weeks/` or the `.db`. Rebuild `weeks/` after ANY change to the canonical CSVs. Each
subfolder has its own `CLAUDE.md`/`SCHEMA.md`.

## Keeping it current
`python3 fetch_new.py --probe` (default; read-only) lists PMN notices with a meeting date newer
than the index max for each dataset (council body 388, PC body 389). `--fetch [--dataset …]`
opens each new notice, downloads a **Meeting-Minutes** attachment (an agenda/packet-only notice is
"pending" — logged, never stubbed), converts `pdftotext -layout` → markdown → `minutes_index.csv`,
then runs `extract_votes.py` + `validate_votes.py`. Rebuild db + weeks afterward (the CLI prints
the reminder). ⚠ **PMN posts minutes AFTER the meeting** (recent 2026 meetings show as pending),
and **PC minutes post to PMN only intermittently** (2020/2021/2023 PC minutes never reached PMN —
a real upstream gap; **2020-01→09 + 2021-01→06 were recovered from the former city WordPress site
via Wayback and promoted 2026-07-16** (`source=wayback` index rows, `provenance=wayback_minutes`
vote rows); 2020 H2 / 2021 H2 / all of 2023 remain genuinely unrecoverable).

## Analysis guidance
- Councils are high-consensus — **contested votes (any Nay/Abstain/Recuse) are the signal**
  (db `v_contested` = 33 motions; 7 contested council + 26 contested PC — 15 of the PC ones
  from the 2020/2021 Wayback-promoted minutes). `summary.md` surfaces
  them per week.
- Coverage seams + honest gaps are documented in `README.md`, `recon.md`, and `VERIFICATION.md`
  — read those before quantitative claims (especially the voting-mayor roll of 6, the Jan-2026
  turnover, the prose-results style, and the PC PMN gap).
- Comments are **honest-empty** (submit-only) — see `public_comments/AVAILABILITY.md`; treat as a
  legitimate zero, not a gap.
